## Goal

Build the centralized protective-order manager. Every automated live long entry with required protection must have broker-held sell protection for the actual confirmed remaining quantity or the entry must fail closed when unsupported. Protection is attached to PositionCycle and runs independently of BUY/SELL strategy cadence, pause, and minimum hold. Support fixed, preferred trailing_native, and later trailing_stepped modes through one provider-neutral ProtectionPolicy; maintain exactly one effective full-position protective sell order so two competing sells cannot oversell. For fixed protection, calculate from a defined reference such as confirmed fill using percent/USD/ATR/support policy where configured, round to broker tick rules, and reconcile coverage after each partial/full fill. Stop-market and stop-limit semantics/risks are explicit; a stop trigger price is not a guaranteed execution or max loss. Fractional protective order/TIF/linked-order combinations are capability-gated and rejected in live when not paper-proven. DAY stop expiry/overnight residual is explicit PROTECTION_EXPIRED/OVERNIGHT risk. For Alpaca trailing_native, submit standalone trailing_stop SELL using exactly one of trail_price or trail_percent and read authoritative broker hwm, stop_price, status, TIF, and protected quantity. Native trailing is continuous broker-managed behavior and continues only while the broker order remains active; it must not be represented as stepped and must not be attached as an unsupported OTO/bracket/OCO trailing leg. Persist protection state and expose PENDING/ACTIVE/UPDATING/UNCONFIRMED/TRIGGERED/EXPIRED/UNPROTECTED/OFFLINE conditions. If stop placement/coverage fails after a fill, surface UNPROTECTED_POSITION, block fresh entries, and reconcile rather than concealing the gap. Materialize exactly the five distinct task_hints for this phase; do not merge hints or create extra implementation tasks. Each generated task must have a nonempty implementation description, exact concrete allowed_write_paths drawn only from expected_changed_files, task-specific measurable acceptance_criteria, focused verification_commands, explicit dependencies matching async_notes, and a reasonable task_timeout_seconds. Use allowed_symbols, forbidden_changes, and a bounded decision budget where they reduce ambiguity. Verification-only work must create a real test or audit artifact. Use targeted verification only during this phase; no broad full-suite runs, large backtests, live orders, or paid data acquisition as incidental checks. This PLAN_SKELETON.json is the complete materialization contract for the phase: do not require, request, or consult any external requirements document to understand scope.
