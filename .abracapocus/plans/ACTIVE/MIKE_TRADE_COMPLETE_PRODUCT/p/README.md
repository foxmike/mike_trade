# p

## Goal

Implement a complete local SHADOW Broker/account mode that never calls Alpaca order submission. Each named scenario has starting cash set once, explicit adjustments, independent account/scenario ID, budgets, strategy assignments, entry limits/loss streaks/cooldowns, orders, fills, positions, protection, cash/equity, realized/unrealized P&L, fee/slippage assumptions, and restart-safe ledger. Multiple scenarios may consume the same real-time shared market snapshot concurrently while all account/decision state remains isolated from each other and from paper/live. Simulate market/limit execution from contemporaneous quote data: buys prefer ask, sells bid, with configurable latency/slippage, liquidity participation/size policy, session restrictions, whole/fraction precision, pending/partial fill semantics where evidence allows, and no negative cash/margin unless explicitly configured. Do not fill at candle close merely because a bar crossed. If quote/size evidence cannot support a confident fill, use conservative/no-fill/uncertain behavior and record simulator version/assumptions/feed provenance. Simulate fixed, native-continuous-equivalent, and stepped trailing protection using the same provider-neutral policies used by production, with explicit assumptions for stop trigger and slippage. Shadow estimates must be labeled estimated rather than broker-confirmed. Restart cannot reset balance or positions. Dashboard/report state must clearly separate scenarios and enable live-vs-shadow comparison without merging balances. Include tests proving scenario isolation, exact cash/position accounting, restart persistence, independent eligibility counters, and absolute nonexecution against live broker paths. Materialize exactly the five distinct task_hints for this phase; do not merge hints or create extra implementation tasks. Each generated task must have a nonempty implementation description, exact concrete allowed_write_paths drawn only from expected_changed_files, task-specific measurable acceptance_criteria, focused verification_commands, explicit dependencies matching async_notes, and a reasonable task_timeout_seconds. Use allowed_symbols, forbidden_changes, and a bounded decision budget where they reduce ambiguity. Verification-only work must create a real test or audit artifact. Use targeted verification only during this phase; no broad full-suite runs, large backtests, live orders, or paid data acquisition as incidental checks. This PLAN_SKELETON.json is the complete materialization contract for the phase: do not require, request, or consult any external requirements document to understand scope.
