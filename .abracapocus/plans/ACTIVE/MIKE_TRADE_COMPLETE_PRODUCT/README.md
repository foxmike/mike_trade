# MIKE_TRADE_COMPLETE_PRODUCT

## Purpose

Build the complete production-grade, operator-supervised mike_trade stock-trading application as one maintainable Python 3.12+ product for Ubuntu, primarily the Dell PowerEdge R730 and also the development desktop. This PLAN_SKELETON.json is intentionally self-contained and is the sole product contract required for plan materialization; no external requirements document is required. The application monitors roughly 1-10 operator-selected U.S. equities, acquires market data once per symbol, computes shared candles/indicators, evaluates independently configurable Python BUY and SELL strategy classes, and manages one intentional long entry followed by one complete discretionary exit per position cycle. No averaging down, pyramiding, planned scaling, or planned partial exits; broker partial fills must be handled correctly. Initial active trading is long-only, while type/capability boundaries may anticipate future short/cover support without enabling it. Strategies never call brokers or open their own data connections. Use ports/adapters and dependency injection so brokerage, market data, optional research, persistence, clocks, and execution modes are replaceable. Alpaca Trading API is the initial equity broker and Alpaca Basic IEX is the initial live market-data feed; paper and live endpoints/credentials/ledgers are strictly isolated. IEX provenance must be preserved because it is not consolidated SIP. The engine uses a shared market-data service/cache, centralized candle/indicator computation, one internal scheduler, bounded concurrent strategy evaluation, and serialized account/portfolio/order mutations. All money, share quantities, fees, fills, and budgets use Decimal; event times are timezone-aware UTC with America/New_York/exchange-session presentation and scheduling. Risk and lifecycle controls include per-symbol and total application budgets, broker buying-power checks, optional planned-loss sizing, max open positions, daily loss guard, configurable max filled entry cycles per symbol/session, consecutive losing-trade entry lockouts by symbol and optionally originating buy strategy, post-sale cooldown, minimum hold for ordinary strategy exits only, regular-hours operation, entry cutoff, and optional end-of-day close disabled by default. Entry blocks never disable fills, stops, reconciliation, manual closes, or safety exits. Every automated live long position requires broker-held protective coverage when the configured provider capability can support it. Support fixed stops, preferred broker-native continuous trailing stops, and provider-neutral stepped trailing stops. Protection begins after confirmed positive fill, covers actual remaining quantity, never moves downward for a long position, survives engine offline only to the extent the last confirmed broker order remains active, and is coordinated with discretionary/manual exits so overlapping sells cannot create a short position. Unsupported fractional/order combinations fail closed and remain unavailable until demonstrated in Alpaca paper. Provide four distinct modes: deterministic historical backtest with no broker access; local SHADOW accounts using the live shared feed and persistent simulated ledgers; Alpaca PAPER using the broker paper environment; and explicitly authorized Alpaca LIVE. Cross-mode credentials, account state, positions, orders, balances, limits, and ledgers must never leak. Multiple named shadow scenarios may run concurrently on one shared data stream. Persist durable restart-safe state in SQLite WAL with one authoritative writer, migrations, append-only/auditable trade-affecting events, idempotent broker activity ingestion, backups/restore checks, read projections, and no bulk raw tick archive. Broker truth is authoritative for live orders/positions; discrepancies create explicit reconciliation drift and block new entries until resolved. Ship real reusable strategy plugins, including an actual reference pair: vwap_bounce BUY triggers only when a completed 1-minute regular-session bar crosses upward through session VWAP (prior close <= prior VWAP and latest close > latest VWAP); vwap_breakdown SELL triggers on the inverse downward crossing. Both use shared warmed/fresh completed-bar context, never fetch data or submit orders, suppress duplicate signals on the same bar, and are independently registered/pairable through vwap_reference. Include a shadow-only reference configuration and deterministic end-to-end shadow/replay evidence; never claim profitability merely because a strategy is implemented. Provide a real separate production dashboard process: FastAPI supplies a read-only API and serves a compiled React + TypeScript + Vite frontend. The dashboard is not a demo or static mock and must not require a Vite development server in deployment. It remains reachable if the engine dies, independently determines OFFLINE from heartbeat age, clearly marks stale last-known values, supports account/scenario switching without mixed balances, and shows account KPIs, 1-10 symbol watch status, signals, positions, orders, protective/trailing state, eligibility limits, P&L, health, reconciliation, and recent trade detail. It never places orders or mutates configuration. Do not build a professional charting terminal. The Makefile/CLI is the operator surface for install/doctor, service lifecycle, dashboard, configuration, providers, strategies, symbols, shadow/paper/live modes, pause/resume and entry kill switch, positions/orders/balance/budget, close/close-all/flatten, trailing-stop inspection/reconcile/policy, entry-limit/cooldown controls, reconciliation, bounded history/logs, reports/exports, backtests, cache, database maintenance, tests, and systemd service management. Make recipes delegate to application services/CLI and do not contain business logic. Live-mutating commands require explicit live confirmation. Operational behavior is fail-closed for new entries on stale/unknown data, unresolved orders, unreconciled broker state, unknown stop state, unsafe account flags, or insufficient buying power. Shutdown does not implicitly liquidate or cancel valid broker-held protective stops. Startup reconciles broker account, positions, orders, fills, stops, budgets, and persistent strategy state before permitting new entries. External positions are UNMANAGED until explicit adoption/handling. Completion requires functional implementation, positive and negative tests, persisted/auditable behavior, documented controls, reporting/dashboard integration where appropriate, reproducible dependency locks, migrations, deployment/service files, operator documentation, deterministic end-to-end shadow evidence, and credential-gated Alpaca paper verification. Mocks do not count as broker integration, static dashboard examples do not count as a dashboard, and hardcoded BUY fixtures do not count as production strategies. Explicitly out of scope unless separately approved: options/futures/crypto, automated stock screening, mandatory ML/LLM decision-path inference, browser broker automation, exchange/microsecond smart routing, capital transfers, mandatory notifications, earnings/economic blackout automation, full-session raw tick recording, configuration-history/diff/preview product, dedicated charting terminal, and automatic live short selling.
