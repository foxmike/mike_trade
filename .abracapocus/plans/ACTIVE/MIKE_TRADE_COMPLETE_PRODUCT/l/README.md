# l

## Goal

Implement transactional capital sizing and entry-eligibility policies for each execution account/scenario and symbol. total_budget_usd caps this application's managed open-position plus pending-entry commitment for the account/scenario; symbol_budget_usd caps one symbol's single entry cycle with no topping up. Broker cash/buying power remains authoritative and includes external/unmanaged holdings where relevant. Reservations cover pending buys and actual filled notional transactionally and release unused amounts on final cancel/partial fill. Size a long entry from remaining symbol budget, remaining total budget, broker buying power, configured reserve/slippage cushion, allowed share precision, and optional/required max_planned_loss_usd relative to validated stop distance. Round down to a supported positive quantity; reject if below minimum order value, insufficient buying power, fractional/trailing protection is unsupported, or protection cannot be established. Margin is disabled unless explicitly configured. Multiple simultaneous eligible signals are processed under a shared budget lock with deterministic symbol/strategy priority. Implement max_entry_cycles_per_day per account/scenario+symbol using New York exchange session: first confirmed positive partial buy fill consumes exactly one slot, later partials are same cycle, zero-fill rejected/canceled orders consume none, and restart cannot reset the count. Implement consecutive negative-net realized cycle lockout per symbol and optional originating BUY strategy scope: negative increments, positive resets, exact breakeven leaves unchanged, unavailable/estimated fees are explicit; reset mode next_session or audited manual. Implement post_sale_cooldown_seconds from final closing fill, persistent across restart and applying after any exit. Implement account daily loss, max open positions, spread/liquidity, regular-hours, entry cutoff/early-close, and discretionary minimum-hold policies. These entry blockers never stop fills, protection, reconciliation, manual close, or risk exits. Materialize exactly the five distinct task_hints for this phase; do not merge hints or create extra implementation tasks. Each generated task must have a nonempty implementation description, exact concrete allowed_write_paths drawn only from expected_changed_files, task-specific measurable acceptance_criteria, focused verification_commands, explicit dependencies matching async_notes, and a reasonable task_timeout_seconds. Use allowed_symbols, forbidden_changes, and a bounded decision budget where they reduce ambiguity. Verification-only work must create a real test or audit artifact. Use targeted verification only during this phase; no broad full-suite runs, large backtests, live orders, or paid data acquisition as incidental checks. This PLAN_SKELETON.json is the complete materialization contract for the phase: do not require, request, or consult any external requirements document to understand scope.
