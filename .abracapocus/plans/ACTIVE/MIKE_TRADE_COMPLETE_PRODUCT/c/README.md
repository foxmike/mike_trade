# c

## Goal

Implement SQLite WAL persistence as the durable source for application state and audit history with one authoritative writer per operational database, forward-only migrations, foreign keys, integrity checks, indexed UTC timestamps, transactions, backups, restore rehearsal, and read-only projections. Separate LIVE, PAPER, each named SHADOW scenario, and BACKTEST runs by explicit account/scenario/run keys; cross-mode writes are forbidden. The schema/repositories must support run configuration fingerprints, operator commands, service health, instruments/capabilities, compact market observations/candles where needed for evidence, strategy instances/evaluations, signals and decisions, position cycles, account reservations, order intents, broker orders/order events, fills keyed by unique external activity ID, protection orders, trailing-stop state/events, positions read model, cash events, equity snapshots, reconciliation runs, persistent strategy state/rearm, entry-eligibility counters/lockouts/cooldowns, and backtest manifests. Do not create a bulk raw tick archive. Persist order intent before broker submission; apply broker activity/fills idempotently; update budget reservations, fills, position cycles, protection, and account projections atomically where required. Failed journal writes must not permit unrecorded accepted live intent. Broker/local discrepancies are explicit drift, not silently rewritten history. Read projections must support dashboard/report queries while the engine owns writes. Backup/restore and maintenance commands must preserve ledger/account isolation and detect corruption. Materialize exactly the five distinct task_hints for this phase; do not merge hints or create extra implementation tasks. Each generated task must have a nonempty implementation description, exact concrete allowed_write_paths drawn only from expected_changed_files, task-specific measurable acceptance_criteria, focused verification_commands, explicit dependencies matching async_notes, and a reasonable task_timeout_seconds. Use allowed_symbols, forbidden_changes, and a bounded decision budget where they reduce ambiguity. Verification-only work must create a real test or audit artifact. Use targeted verification only during this phase; no broad full-suite runs, large backtests, live orders, or paid data acquisition as incidental checks. This PLAN_SKELETON.json is the complete materialization contract for the phase: do not require, request, or consult any external requirements document to understand scope.
