# f

## Goal

Build the provider-neutral order-management subsystem above Broker. Persist every OrderIntent before network submission and implement the exact lifecycle INTENT_PERSISTED -> SUBMITTING -> ACCEPTED/PENDING -> PARTIALLY_FILLED -> FILLED, with REJECTED, CANCEL_PENDING, CANCELED, EXPIRED, REPLACED, SUSPENDED, and UNKNOWN branches. Consume deduplicated provider event/activity IDs and tolerate out-of-order broker updates without inferring fills from acceptance. Serialize entry and exit authorization per execution account + symbol and serialize shared cash reservation decisions account-wide so concurrent strategies cannot double-spend. Stale/expired signals and stale quotes must be rechecked immediately before submit. An unknown submit result requires lookup/reconciliation by stable client_order_id, never blind resubmission. A cancel request is not cancellation; replacement success response is not final replacement confirmation. Fill processing is exactly-once at the application level and drives actual held quantity, cost basis, reservations, position cycle state, and later protection. Handle partial fills, rejected/canceled zero-fill orders, partial then cancel, duplicate updates, and server crash after persisted intent but before response. Never allow an EXIT_LONG request or protective-stop race to sell more than the confirmed remaining long quantity or accidentally establish a short. Add deterministic fault fixtures for ambiguous submit, duplicate/out-of-order events, cancel/fill races, and lifecycle recovery. Materialize exactly the five distinct task_hints for this phase; do not merge hints or create extra implementation tasks. Each generated task must have a nonempty implementation description, exact concrete allowed_write_paths drawn only from expected_changed_files, task-specific measurable acceptance_criteria, focused verification_commands, explicit dependencies matching async_notes, and a reasonable task_timeout_seconds. Use allowed_symbols, forbidden_changes, and a bounded decision budget where they reduce ambiguity. Verification-only work must create a real test or audit artifact. Use targeted verification only during this phase; no broad full-suite runs, large backtests, live orders, or paid data acquisition as incidental checks. This PLAN_SKELETON.json is the complete materialization contract for the phase: do not require, request, or consult any external requirements document to understand scope.
