# d

## Goal

Implement versioned, strictly validated YAML configuration and durable operator-control contracts. Configuration must cover service timezone/data directory/dashboard bind and heartbeat thresholds; market-data provider/feed/mode/freshness/warmup/timeframes; optional research providers; scheduler cadence/worker/queue settings; execution broker and account mode shadow|paper|live; fractional permission; order types; regular-hours-only; entry cutoff; optional end-of-day close disabled by default; stop-required and block-new-entries-when-unprotected; margin disabled by default; account risk limits; per-symbol budgets, planned-loss cap, min hold, entry-cycle cap, consecutive-loss limit/reset mode, post-sale cooldown, independently selected buy/sell strategies, and fixed/native/stepped stop policy; strategy parameters; named shadow scenarios and starting cash; and reporting/evidence retention. Secrets never live in YAML and are supplied by environment/OS-protected service configuration. Precedence is defaults -> main config -> optional mode config -> secret/runtime environment -> explicit one-shot CLI overrides. Persist an SHA-256 fingerprint/redacted effective trade-relevant config for audit, but do not build a configuration-history/diff/rollback or preview product. Safe config mutations are atomic, schema-validated, audited, and must refuse changes that orphan an open position/protective stop or silently enable live trading. Implement durable idempotent ControlCommand/inbox behavior for pause/resume, entry disable/enable, guarded config changes, and later operator commands. When engine is offline, status/read operations remain possible; never silently queue an executable live trade for reconnection. Provide redacted config-show behavior and example config/provider/.env templates with names only, no secrets. Materialize exactly the five distinct task_hints for this phase; do not merge hints or create extra implementation tasks. Each generated task must have a nonempty implementation description, exact concrete allowed_write_paths drawn only from expected_changed_files, task-specific measurable acceptance_criteria, focused verification_commands, explicit dependencies matching async_notes, and a reasonable task_timeout_seconds. Use allowed_symbols, forbidden_changes, and a bounded decision budget where they reduce ambiguity. Verification-only work must create a real test or audit artifact. Use targeted verification only during this phase; no broad full-suite runs, large backtests, live orders, or paid data acquisition as incidental checks. This PLAN_SKELETON.json is the complete materialization contract for the phase: do not require, request, or consult any external requirements document to understand scope.
