# o

## Goal

Implement provider-independent trailing_stepped protection as an alternative to native continuous trailing. Configuration supplies per-symbol trailing distance (USD or percent), upward step increment (USD or percent), replacement minimum interval, TIF, and broker capability requirements. Persist entry reference, observed high_watermark, ratchet_anchor, desired candidate stop, last broker-confirmed stop, protected quantity, broker order ID/status, policy revision, and every ratchet/replacement event. The ratchet is monotone for a long position: initial stop derives from entry reference minus distance; advance only after one or more complete configured favorable steps; a single price jump may cross multiple steps; sub-step highs do not reprice; price declines never lower the stop. Canonical USD example must pass exactly: entry 100, distance 2, step 1 -> stop 98; high 100.80 stays 98; high 101 -> 99; high 103.20 -> 101; later decline leaves 101. Broker rounding is applied before comparing a new candidate to last confirmed stop. Stepped protection must use a verified broker-held standalone stop and capability-checked replace workflow; never pretend an in-process threshold is equivalent protection. Replacement intent is persisted, then provider status/trade update/order lookup confirms the new stop before it is considered effective. Unknown/rejected replacement preserves last verified protection when still active, blocks conflicting actions/new entries, marks TRAIL_UPDATE_UNCONFIRMED, and reconciles. Do not accumulate duplicate pending replacement requests. Handle stop fill during cancel/replace, discretionary/manual close race, partial fills, orphan orders, and restart. On engine offline the last confirmed broker stop may remain active, but step advancement is suspended and dashboard must say TRAIL_STALE/OFFLINE. Materialize exactly the five distinct task_hints for this phase; do not merge hints or create extra implementation tasks. Each generated task must have a nonempty implementation description, exact concrete allowed_write_paths drawn only from expected_changed_files, task-specific measurable acceptance_criteria, focused verification_commands, explicit dependencies matching async_notes, and a reasonable task_timeout_seconds. Use allowed_symbols, forbidden_changes, and a bounded decision budget where they reduce ambiguity. Verification-only work must create a real test or audit artifact. Use targeted verification only during this phase; no broad full-suite runs, large backtests, live orders, or paid data acquisition as incidental checks. This PLAN_SKELETON.json is the complete materialization contract for the phase: do not require, request, or consult any external requirements document to understand scope.
